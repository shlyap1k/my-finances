# Architecture

## Цель системы

Личный финансовый планировщик, который:

- хранит регулярные доходы пользователя;
- хранит обязательные регулярные расходы;
- хранит накопительные счета и правила перевода части доходов на них;
- хранит обычные и плановые транзакции;
- умеет считать прогноз доступного остатка на будущую дату;
- отвечает на вопрос: хватит ли денег к определенной дате с учетом будущих доходов, обязательных платежей, переводов в накопления, плановых трат и среднего расхода в день.

Система многопользовательская: каждый пользователь видит только свои данные.

---

## Основные продуктовые ограничения MVP

1. Одна базовая валюта.
2. Проценты по накопительным счетам не учитываются.
3. Стартовый баланс пользователя равен 0.
4. Фактический остаток считается по транзакциям.
5. Регулярные доходы наступают автоматически по дате.
6. Обязательные расходы уменьшают фактический баланс только после подтверждения.
7. Пользователь самостоятельно добавляет:
    - обычные фактические траты;
    - плановые траты;
    - переводы между основным балансом и накопительными счетами при необходимости.
8. Повторяющиеся события привязаны к дням месяца.
9. Если день месяца 29, 30 или 31, а в месяце меньше дней, событие переносится на последний день месяца.

- Go 1.23+
- Gin
- PostgreSQL 16

## Схема запуска в разработке

Postgres поднимается в Docker:

```bash
docker compose up -d postgres
```
Приложение запускается локально:

Или через дебаггер.
Порт приложения: 8040.
Порт Postgres наружу: 5488.
Внутри контейнера Postgres использует стандартный порт 5432.
Пример строки подключения из приложения:

Docker Compose
В разработке в Docker живет только база.
Пример docker-compose.yml

```yaml
services:
  postgres:
    image: postgres:16
    container_name: finance_db
    environment:
      POSTGRES_DB: finance
      POSTGRES_USER: finance
      POSTGRES_PASSWORD: finance
    ports:
      - "5488:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U finance -d finance"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  pgdata:
```

Пароль БД для локальной разработки может быть простым, но он не должен быть захардкожен в коде приложения. 
Приложение читает DATABASE_URL из окружения.

Компоненты приложения
Рекомендуемая структура:

```text
cmd/
  api/
    main.go

internal/
  config/
  auth/
  http/
    handlers/
    middleware/
    dto/
  domain/
    projection/
  store/
    postgres/
    queries/

migrations/
docs/
web/
  templates/
  static/
```
Основные слои
cmd/api
Точка входа:

    читает конфигурацию;
    применяет миграции или вызывает их отдельно;
    поднимает HTTP-сервер на :8040.

internal/config
Чтение переменных окружения.
internal/auth

    bcrypt password hashing;
    генерация JWT;
    валидация JWT;
    работа с cookie.

internal/http
Gin-роутер, middleware, обработчики API.
internal/domain/projection
Чистая бизнес-логика прогноза:

    генерация повторений по дням месяца;
    расчет переводов на накопительные счета;
    расчет среднего расхода;
    прогноз доступного баланса;
    расчет enough, shortfall, min_balance_in_period, warnings.

Этот пакет не должен зависеть от HTTP и базы данных.
internal/store/postgres
Доступ к PostgreSQL через pgx и sqlc.

Аутентификация
Используем JWT.
Claims:

json
1
2
3
4
5

Где:

    sub — user id;
    iat — issued at;
    exp — expiration.

Подпись: HS256.
Секрет подписи хранится в переменной окружения JWT_SECRET.
JWT передается через HttpOnly cookie.
Имя cookie: auth_token.
Параметры cookie:

    HttpOnly: true;
    Path: /;
    SameSite: Lax;
    Secure: true в production, false локально.

Logout просто удаляет cookie. Server-side revocation не делаем.
Пароли хэшируем bcrypt.

Авторизация и изоляция пользователей
Все пользовательские данные имеют user_id.
Каждый запрос к приватным данным должен:

    распарсить JWT;
    достать user_id;
    передать user_id в слой данных;
    выполнять все SQL-запросы с фильтром WHERE user_id = $1.

Чужие записи API должен возвращать как 404 Not Found, а не 403 Forbidden, 
чтобы не раскрывать существование чужих объектов.


## Миграции
### Используем goose.
Каталог:
```text
migrations/
```

Команды:
```bash
goose -dir migrations postgres "$DATABASE_URL" up
goose -dir migrations postgres "$DATABASE_URL" down
goose -dir migrations postgres "$DATABASE_URL" status
```
##sqlc
###sqlc используется для уменьшения ошибок в SQL.
Пример структуры:

```text
internal/store/postgres/
  queries/
    users.sql
    income_rules.sql
    expense_rules.sql
    savings_accounts.sql
    savings_rules.sql
    transactions.sql
```

После написания запросов:

```bash
sqlc generate
```
ИИ-агентам запрещено запускать эту команду! Если разработка упирается в генерацию, то необходимо остановиться, 
сделать пулл реквест и попросить человека на своем компе сделать эти генерации!

Важное правило:

    обычные CRUD-запросы делаем через sqlc;
    сложные прогнозные выборки можно писать отдельно, но они все равно обязаны фильтровать данные по user_id.



Основные архитектурные правила

    Никаких float для денег.
    Все приватные запросы фильтруются по user_id.
    Бизнес-логика прогноза находится в internal/domain/projection.
    HTTP-обработчики не считают прогноз вручную.
    SQL-запросы не должны содержать бизнес-логику прогноза.
    Регулярные события и транзакции не должны смешиваться в одну сущность.
    Все даты денежных событий храним как date.
    Расчеты ведутся в таймзоне пользователя.
    API сохраняет плановую транзакцию даже если денег не хватает.
    Недостаток денег — это warning / projection result, а не ошибка валидации.
