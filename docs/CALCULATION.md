# Calculation

Этот документ описывает, как считается доступный баланс и прогноз.

---

## Базовые принципы

1. Все суммы — integer minor units.
2. Все расчеты ведутся в таймзоне пользователя.
3. `as_of_date` — сегодняшняя дата пользователя.
4. `target_date` — дата, на которую нужно проверить доступность денег.
5. `target_date` не может быть раньше `as_of_date`.
6. Стартовый баланс пользователя равен 0.
7. Фактический баланс считается по транзакциям.
8. Регулярные доходы наступают автоматически.
9. Обязательные расходы уменьшают фактический баланс только после подтверждения.
10. Плановые транзакции учитываются в прогнозе, но не считаются фактическим балансом.

---

## Фактический баланс

Фактический основной баланс на дату `X`:

```text
main_balance(X) =
    sum(actual income with occurred_on <= X)
  - sum(actual expense with occurred_on <= X)
  - sum(actual savings_deposit with occurred_on <= X)
  + sum(actual savings_withdraw with occurred_on <= X)
```
Для UI можно отдавать фактический баланс на as_of_date.
Для проекции удобнее считать baseline на конец дня перед as_of_date, а затем отдельно обрабатывать события сегодняшнего дня.

##Средний расход в день
Средний расход считается только из операций, которые одновременно:

```text
kind = expense
status = actual
origin = manual
exclude_from_average = false
```

Обязательные платежи не участвуют.
Переводы на накопительные счета не участвуют.
Плановые операции не участвуют.
Окно по умолчанию — 30 дней.
Используем последние 30 завершенных дней до as_of_date:
window_start = as_of_date - 30 days
window_end = as_of_date - 1 day

avg_daily_spend_minor = ceil(total_expenses_minor / avg_window_days)

Округление вверх — консервативное.
Если данных нет:
avg_daily_spend_minor = 0

Если include_avg = true, средний расход вычитается за каждый день
avg_daily_spend_minor * days_count


##Регулярные доходы
Для каждого активного income rule система определяет даты наступления в диапазоне проекции.
Правило:
monthly_day = N

Если в месяце нет дня N, используется последний день месяца.

Пример расчета накоплений
Дано:
gross income = 100000 рублей = 10_000_000 minor units

правила:
1. 10% в подушку
2. 5000 в отпуск
3. 20% в инвестиции

Расчет:

income = 10_000_000

rule 1: 10% = 1_000_000
remaining = 9_000_000

rule 2: fixed = 500_000
remaining = 8_500_000

rule 3: 20% от исходного дохода = 2_000_000
remaining = 6_500_000

Итог:

    на накопления ушло 3_500_000;
    от дохода осталось 6_500_000.

Материализация переводов на накопительные счета
Когда регулярный доход материализуется как фактический, система также материализует переводы по savings rules.
Создается транзакция:

kind = savings_deposit
status = actual
origin = savings_rule
occurred_on = дата дохода
amount_minor = рассчитанная сумма перевода
savings_account_id = счет накопления
source_income_rule_id = доход
savings_rule_id = правило

Обязательные расходы
Обязательные расходы хранятся в expense rules.
В прогнозе они уменьшают доступный баланс автоматически.
В фактическом балансе они уменьшают баланс только после подтверждения.
Подтверждение создает транзакцию:

kind = expense
status = actual
origin = obligation_confirmation
source_expense_rule_id = id обязательного правила
source_rule_occurred_on = дата планового события

Если обязательный расход подтвержден для плановой даты D, проекция не списывает expense rule для даты D повторно.

Плановые и обычные транзакции
Пользователь может создавать транзакции вручную.
Обычная фактическая трата
Пример: купил бургер сегодня.

```text
kind = expense
status = actual
origin = manual
occurred_on = today
```

Такие операции:

    уменьшают фактический баланс;
    участвуют в расчете среднего расхода, если exclude_from_average = false.

Плановая трата
Пример: покупка iPhone 10 сентября.

kind = expense
status = planned
origin = manual
occurred_on = future date

Такие операции:

    не уменьшают фактический баланс;
    уменьшают прогнозный баланс на дату события.

Ограничения и допущения MVP

    Регулярные доходы считаются наступившими автоматически.
    Если доход не пришел в жизни, пользователь должен скорректировать это вручную.
    Обязательные расходы не считаются фактически списанными без подтверждения.
    Savings rules применяются к еще не материализованным будущим доходам по текущим правилам.
    Изменение savings rules не переписывает уже материализованные прошлые переводы.
    Если пользователь хочет изменить прошлое, используются корректирующие ручные транзакции.
    Средний расход является консервативной оценкой и может частично пересекаться с ручными плановыми тратами.
    Система не блокирует сохранение транзакции, если денег не хватает.
